## 4. PodSecurity Policies: Enforcement and Configuration

### PodSecurityPolicy Definition and Scope

PodSecurityPolicy (PSP) is a Kubernetes resource that defines a set of policies governing how Pods are created and run within a cluster. Introduced in Kubernetes v1.8 as a beta feature, PSP provides a mechanism to enforce security constraints on Pod configurations, ensuring that applications adhere to defined security baselines. The scope of PSP includes controlling the use of privileged containers, specifying allowed volumes and SELinux labels, and enforcing resource limits and scheduling constraints. These policies are applied at the namespace level, meaning that any Pod created within a namespace must comply with the PSP associated with that namespace. The primary purpose of PSP is to mitigate security risks by preventing Pods from running with elevated privileges or using potentially unsafe configurations.

The enforcement of PodSecurityPolicy is achieved through the Kubernetes API server and the kubelet. When a Pod is created, the API server checks whether it complies with the applicable PodSecurityPolicy. If the Pod does not meet the policy requirements, the creation is rejected, and an error is returned to the user. This mechanism ensures that all Pods running within a namespace adhere to the defined security constraints. The enforcement process is further enhanced by the use of admission controllers, which are responsible for validating and mutating requests before they reach the API server. The `PodSecurityPolicy` admission controller is specifically designed to enforce these policies, ensuring that any Pod creation or update operation is validated against the configured PSPs.

The scope of PodSecurityPolicy extends beyond just the enforcement of security constraints. It also includes the ability to specify which users or groups are allowed to create Pods that comply with the policy. This feature is particularly useful in multi-tenant environments where different teams or organizations may have varying security requirements. By associating specific users or groups with a PSP, administrators can ensure that only authorized entities can create Pods that meet the defined security baseline. Additionally, PSPs can be used to enforce quotas on the number of Pods that can be created within a namespace, further enhancing resource management and security.

One of the key aspects of PodSecurityPolicy is its ability to control the use of privileged containers. A privileged container has elevated privileges, allowing it to access all devices on the host system. While this can be useful for certain applications, it also poses a significant security risk if not properly managed. PSPs allow administrators to specify whether privileged containers are allowed within a namespace. This ensures that only trusted applications or services can run with elevated privileges, reducing the attack surface of the cluster.

Another important feature of PodSecurityPolicy is its ability to control the use of specific volumes and SELinux labels. Volumes are used to store data for Pods, and certain types of volumes may pose security risks if not properly configured. PSPs allow administrators to specify which volume types are allowed within a namespace, ensuring that only safe and trusted volumes are used. Similarly, SELinux labels are used to enforce security policies at the operating system level, and PSPs can be configured to restrict the use of certain SELinux labels, further enhancing the security of the cluster.

The enforcement of PodSecurityPolicy is also influenced by the use of admission controllers and the Kubernetes API server. Admission controllers are responsible for validating and mutating requests before they reach the API server. The `PodSecurityPolicy` admission controller ensures that any Pod creation or update operation is validated against the configured PSPs. This mechanism provides a robust way to enforce security constraints across the entire cluster, ensuring that all Pods comply with the defined policies.

In addition to enforcing security constraints, PodSecurityPolicy also includes the ability to specify scheduling constraints. Scheduling constraints allow administrators to define where Pods can be scheduled within the cluster, based on specific criteria such as node labels or resource availability. This feature is particularly useful in environments where certain nodes are reserved for specific workloads or require additional security measures. By specifying scheduling constraints within a PSP, administrators can ensure that Pods are only scheduled on nodes that meet the defined security requirements.

The use of PodSecurityPolicy is further enhanced by the ability to define multiple policies and apply them to different namespaces. This allows administrators to create a flexible and scalable security framework, where different namespaces can have varying security requirements based on their specific needs. For example, a namespace designated for production workloads may have stricter security policies compared to a namespace used for development or testing environments. This approach enables a more granular and effective security strategy, tailored to the specific needs of each namespace.

In summary, PodSecurityPolicy is a critical component of Kubernetes security, providing a mechanism to enforce security constraints on Pod configurations. By controlling the use of privileged containers, specifying allowed volumes and SELinux labels, and enforcing resource limits and scheduling constraints, PSPs help mitigate security risks within a cluster. The enforcement of these policies is achieved through the Kubernetes API server and admission controllers, ensuring that all Pods comply with the defined security baselines. The ability to associate specific users or groups with a PSP further enhances the security of multi-tenant environments, while the use of scheduling constraints allows for more flexible and targeted security management. By leveraging PodSecurityPolicy, administrators can create a robust and scalable security framework, tailored to the specific needs of their Kubernetes environment.

### Enforcement Modes and Admission Controllers

The enforcement of PodSecurity policies within Kubernetes is fundamentally tied to the architecture and operational design of admission controllers. Admission controllers are a critical component of the Kubernetes API server that intercept requests before they are persisted to the etcd store. These controllers enforce constraints, validate data, and mutate objects as needed. In the context of PodSecurity policies, the primary enforcement mechanism is the `PodSecurity` admission controller, which ensures that pods adhere to defined security profiles such as `baseline`, `restricted`, or `privileged`. This controller operates by validating pod specifications against the configured PodSecurity policy, thereby enforcing a consistent security posture across the cluster.

The `PodSecurity` admission controller is part of the Kubernetes core components and is typically enabled by default in many distributions. However, its behavior can be fine-tuned through configuration parameters such as `enforce`, `audit`, or `dryRun`. When set to `enforce`, the controller actively blocks the creation or update of pods that do not meet the specified PodSecurity policy. This mode ensures strict compliance with security baselines, making it ideal for regulated or air-gapped environments where deviation from defined policies could introduce vulnerabilities.

In addition to the `PodSecurity` admission controller, the Kubernetes ecosystem includes other admission controllers such as `ValidatingAdmissionWebhook` and `MutatingAdmissionWebhook`. These controllers are often used in conjunction with external policy engines like Open Policy Agent (OPA) or Kyverno to provide more granular and flexible enforcement capabilities. For instance, `ValidatingAdmissionWebhook` allows for custom validation logic to be applied to pod specifications, enabling the enforcement of complex security policies that may not be expressible through standard PodSecurity profiles.

The interaction between admission controllers and PodSecurity policies is further enhanced by the use of admission controller chains. A chain is a sequence of admission controllers that are executed in a specific order. The `PodSecurity` admission controller can be positioned within this chain to ensure that pod creation or update requests are validated before they are processed by other controllers. This allows for layered enforcement, where multiple policies and constraints can be applied in a coordinated manner.

The configuration of admission controllers is typically managed through the Kubernetes API server configuration file (`kube-apiserver.yaml`). Parameters such as `--enable-admission-plugins` specify which admission controllers are active. For example, setting `--enable-admission-plugins=PodSecurity,ValidatingAdmissionWebhook` enables both the `PodSecurity` controller and the `ValidatingAdmissionWebhook`, allowing for a combination of built-in and custom validation logic. This flexibility is essential in environments where security policies need to be both standardized and adaptable.

In regulated environments, the use of admission controllers is often supplemented with additional mechanisms such as audit logging and policy enforcement at the infrastructure level. For instance, audit logs generated by the Kubernetes API server can be analyzed to detect violations of PodSecurity policies, providing visibility into compliance status. This is particularly useful in air-gapped clusters where real-time monitoring and alerting capabilities are critical for maintaining security.

The enforcement modes of admission controllers also play a crucial role in the overall security architecture of a Kubernetes cluster. The `enforce` mode ensures that all pods must meet the specified PodSecurity policy, while the `audit` mode allows for policy violations to be logged without blocking the request. This mode is often used during the transition period when moving from a less secure baseline to a more stringent one. Similarly, the `dryRun` mode is useful for testing and validating policies before they are applied in production environments.

The effectiveness of admission controllers in enforcing PodSecurity policies is further enhanced by their integration with other Kubernetes components such as the kubelet and kube-proxy. For example, the kubelet enforces security policies at the node level, ensuring that pods running on a node comply with both cluster-wide and node-specific constraints. This multi-layered approach ensures that security policies are enforced across all levels of the Kubernetes architecture.

In summary, the enforcement of PodSecurity policies is deeply intertwined with the operation of admission controllers in Kubernetes. The `PodSecurity` admission controller, along with other mechanisms such as `ValidatingAdmissionWebhook`, provides a robust framework for enforcing security baselines. The configuration and interaction of these controllers are critical for maintaining compliance in regulated and air-gapped environments. By leveraging the flexibility of admission controller chains and integrating with other Kubernetes components, organizations can achieve a comprehensive and enforceable security posture. This foundational architecture not only ensures that pods meet predefined security criteria but also provides the necessary tools for monitoring, auditing, and adapting to evolving security requirements.

### Policy Constraints: Privileged, RunAsUser, and FSGroup

Privileged mode in PodSecurityPolicy (PSP) is a critical configuration parameter that grants elevated privileges to pods, allowing them to bypass certain security constraints. This mode is particularly useful for running containers that require direct access to the host kernel, such as those using device drivers or needing to modify system resources. However, enabling Privileged mode introduces significant security risks, as it allows pods to operate with full root permissions, potentially leading to privilege escalation or unauthorized modifications to the host environment. In bastionkit, the enforcement of Privileged mode is designed to balance operational necessity with security rigor.

The Privileged setting in PSP is a boolean flag that, when set to true, permits the pod to run with elevated privileges. This is often used for legacy applications or specialized workloads that cannot be easily refactored to operate without such privileges. For example, a database container might require access to specific hardware devices or kernel modules, which necessitates running in Privileged mode. In bastionkit, the enforcement of this setting is tied to the broader PodSecurityPolicy framework, ensuring that only explicitly authorized workloads can leverage this elevated state.

The security implications of Privileged mode are substantial. A pod running in Privileged mode can access and modify any file on the host filesystem, interact with hardware devices, and potentially escalate privileges beyond the container's scope. This makes it a prime target for exploitation if not properly controlled. Bastionkit mitigates these risks through strict policy constraints, ensuring that only specific, well-documented workloads are permitted to run in Privileged mode. For instance, bastionkit might define a dedicated PSP for such workloads, limiting their scope to specific namespaces and restricting other potential vulnerabilities.

In addition to the Privileged setting, bastionkit enforces constraints on the RunAsUser and FSGroup parameters within PodSecurityPolicy. These parameters dictate the user identity and file system group that a pod assumes when it runs. The RunAsUser field specifies the user ID (UID) under which the container operates, while the FSGroup field determines the supplementary group that the container belongs to for file system operations. These settings are crucial for isolating processes from the host environment and preventing unauthorized access to critical resources.

The enforcement of RunAsUser in bastionkit is designed to ensure that all containers operate under a non-root user by default, reducing the attack surface in case of vulnerabilities. For example, a container might be configured to run as user 1000, which is a non-root UID, thereby limiting its ability to modify system files or escalate privileges. This approach is aligned with the principle of least privilege, a core tenet of bastionkit's security model. By default, bastionkit policies mandate that containers must specify a valid RunAsUser value, preventing the use of root or arbitrary UIDs that could compromise system integrity.

The FSGroup parameter in bastionkit further enhances security by defining the group permissions for file system operations. This ensures that containers can only access files and directories under the specified group, preventing unauthorized modifications. For instance, a container might be configured to run with an FSGroup of 1001, granting it access to specific resources while restricting access to others. Bastionkit enforces this constraint through strict policy checks, ensuring that any deviation from the defined FSGroup is flagged and addressed.

The interplay between Privileged mode, RunAsUser, and FSGroup in bastionkit's PodSecurityPolicy framework is a testament to its rigorous approach to security. By combining these constraints, bastionkit creates a layered defense mechanism that minimizes the risk of privilege escalation and unauthorized access. For example, a container running in Privileged mode might still be required to operate under a specific RunAsUser and FSGroup, ensuring that even with elevated privileges, the workload remains isolated from critical system resources.

Moreover, bastionkit provides granular control over these parameters, allowing administrators to tailor policies to specific use cases. This flexibility is essential in environments where certain workloads require elevated privileges while others operate under stricter constraints. For instance, a dedicated namespace for privileged workloads might be configured with a custom PSP that allows Privileged mode but restricts RunAsUser and FSGroup to predefined values, ensuring a balance between functionality and security.

In summary, bastionkit's approach to enforcing Privileged mode, RunAsUser, and FSGroup within PodSecurityPolicy is both comprehensive and precise. By meticulously configuring these parameters, bastionkit ensures that containers operate under controlled conditions, minimizing the risk of security breaches while accommodating operational needs. This rigorous enforcement mechanism exemplifies bastionkit's commitment to creating a hardened security baseline for air-gapped Kubernetes environments. The integration of these constraints within the broader PodSecurityPolicy framework underscores bastionkit's ability to deliver robust, scalable security solutions tailored to modern cloud-native workloads.

### Resource Limits and Capabilities Management

Resource limits and capabilities management are integral components of PodSecurity Policies (PSPs) in Kubernetes, ensuring that containers operate within defined resource constraints and possess only necessary privileges. These mechanisms provide a means to prevent resource exhaustion, mitigate privilege escalation risks, and enforce consistency across workloads. By leveraging Kubernetes' built-in capabilities and custom policies, administrators can create a robust framework for managing container behavior. This section delves into the specifics of resource limits and capabilities, highlighting their role in PodSecurity Policy enforcement and configuration.

Resource limits are defined using the `resources` field within a PodSecurityPolicy, which specifies the maximum CPU and memory that a container can consume. These limits act as hard boundaries, preventing any single container from monopolizing cluster resources. For example, a policy might enforce a maximum CPU limit of 2 cores and a memory limit of 4GiB per container. This ensures that even under high load or unexpected behavior, containers do not exceed their allocated resources, thereby maintaining overall system stability. The enforcement of these limits is handled by the Kubernetes kubelet, which monitors container resource usage and enforces the specified constraints.

In addition to CPU and memory limits, PodSecurity Policies also support the configuration of resource requests. Resource requests define the minimum amount of CPU and memory that a container requires to function properly. By setting these requests, administrators ensure that the scheduler can allocate sufficient resources to meet workload demands. For instance, a policy might require a minimum CPU request of 1 core and a memory request of 2GiB for all containers. This helps prevent situations where containers are scheduled on nodes with insufficient resources, leading to performance degradation or failure.

The combination of resource limits and requests provides a balanced approach to resource management. Limits prevent overutilization, while requests ensure that containers have the necessary resources to operate. This dual mechanism is particularly important in environments where resource allocation is critical, such as production clusters or regulated systems. By defining these parameters within PodSecurity Policies, administrators can enforce consistent resource usage across all workloads, ensuring predictable performance and efficient utilization of cluster resources.

Capabilities are another key aspect of PodSecurity Policies, allowing administrators to control the privileges that containers can access. Capabilities are Linux kernel features that grant specific permissions to processes, such as `CAP_NET_BIND_SERVICE` for binding to privileged ports or `CAP_SYS_ADMIN` for administrative tasks. By explicitly defining which capabilities are allowed or denied within a PodSecurity Policy, administrators can restrict containers to only those privileges necessary for their operation. This reduces the attack surface and minimizes the risk of privilege escalation.

For example, a policy might allow the `CAP_NET_BIND_SERVICE` capability to enable a container to bind to port 80, while denying the `CAP_SYS_ADMIN` capability to prevent the container from performing system-level operations. This granular control ensures that containers have only the necessary privileges, reducing the potential for malicious activity or unintended behavior. The enforcement of capabilities is handled by the Kubernetes kubelet, which checks whether a container has been granted the specified capabilities before allowing it to run.

In addition to individual capabilities, PodSecurity Policies also support the use of the `allowPrivilegeEscalation` field, which determines whether a container can escalate its privileges. When set to `true`, this allows a container to gain additional capabilities beyond those explicitly defined in the policy. When set to `false`, it prevents privilege escalation, ensuring that containers remain within their defined boundaries. This feature is particularly useful in environments where containers are expected to run with minimal privileges and where any form of privilege escalation could pose a security risk.

The use of capabilities and privilege escalation control is essential for creating a secure and stable Kubernetes environment. By carefully defining which capabilities are allowed and whether privilege escalation is permitted, administrators can ensure that containers operate within a controlled and predictable environment. This approach not only enhances security but also improves the overall reliability and performance of the cluster.

In practice, the configuration of resource limits and capabilities within PodSecurity Policies requires careful consideration of workload requirements and security constraints. Administrators must strike a balance between providing sufficient resources for workloads to function properly and limiting privileges to prevent potential vulnerabilities. This involves analyzing the specific needs of each application, defining appropriate resource requests and limits, and selecting the necessary capabilities based on the container's operational requirements.

For example, in a regulated environment where containers are expected to run with minimal privileges, administrators might configure PodSecurity Policies to deny all capabilities except those explicitly required for the application to function. This approach aligns with the principle of least privilege, ensuring that containers have only the necessary permissions to perform their tasks. Similarly, in environments where high availability and performance are critical, administrators might set higher resource limits to accommodate peak loads while still maintaining control over resource consumption.

The enforcement of these policies is supported by Kubernetes' built-in mechanisms, including the kubelet and kube-apiserver. The kubelet ensures that containers adhere to the defined resource limits and capabilities, while the kube-apiserver provides the interface for managing and applying PodSecurity Policies across the cluster. This integration allows administrators to enforce consistent security and resource management policies across all nodes and workloads.

In summary, resource limits and capabilities management are essential components of PodSecurity Policies, providing a means to control container behavior and ensure system stability. By defining resource requests and limits, administrators can prevent resource exhaustion and ensure predictable performance. Meanwhile, the configuration of capabilities and privilege escalation control allows for granular security enforcement, reducing the risk of privilege escalation and unauthorized access. Through careful planning and implementation, these mechanisms contribute to a secure and efficient Kubernetes environment, aligning with the principles of hardened security and regulated operations.

### Integration with Kubernetes Admission Controllers

The `PodSecurityAdmission` controller is the most directly relevant admission controller for enforcing PodSecurity Policies. It is responsible for validating that a Pod’s configuration complies with the security constraints defined in a PodSecurityPolicy. The controller operates by evaluating the PodSpec against the rules of the associated PodSecurityPolicy, which may include restrictions on the use of privileged containers, host namespaces, or specific capabilities. When a Pod is created or updated, the `PodSecurityAdmission` controller checks whether the Pod’s configuration meets the security posture defined in the policy. If it does not, the controller rejects the request and returns an error to the user. This mechanism ensures that all Pods within the cluster adhere to a consistent security baseline.

In addition to the built-in `PodSecurityAdmission` controller, Kubernetes provides the ability to extend admission control through the use of ValidatingWebhook and MutatingWebhook admission controllers. These webhooks allow developers and operators to define custom validation and mutation logic for Kubernetes objects, including Pods. Similarly, a MutatingWebhook could be used to automatically apply security-related configurations to Pods, such as setting resource limits or applying security context settings. These webhooks can be integrated with existing PodSecurityPolicy frameworks to create a more granular and flexible security enforcement model.

The configuration of admission controllers for PodSecurity Policies involves several key steps. First, the appropriate admission controller must be enabled in the Kubernetes API server configuration. The integration of admission controllers with PodSecurity Policies is also influenced by the use of Kubernetes’ `ValidatingAdmissionWebhook` and `MutatingAdmissionWebhook` mechanisms. This approach provides greater flexibility in defining security policies and allows for the integration of third-party security tools into the Kubernetes enforcement pipeline.
