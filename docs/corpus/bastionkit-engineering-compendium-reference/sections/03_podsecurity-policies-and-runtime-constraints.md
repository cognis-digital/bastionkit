## 3. PodSecurity Policies and Runtime Constraints

### PodSecurityPolicy Architecture and Design

The PodSecurityPolicy (PSP) architecture within Kubernetes is a foundational mechanism for enforcing security constraints at the pod level. Unlike its successor, the PodSecurity admission controller, which operates on a more abstract and generalized model, PSP provides granular control over the security posture of pods by defining specific policies that govern the capabilities and privileges associated with each pod. The core design of PSP revolves around three primary components: the policy definition, the admission controller, and the enforcement mechanism. These elements work in concert to ensure that only pods meeting predefined security criteria are allowed to run within a Kubernetes cluster.

At the heart of the PSP architecture is the `PodSecurityPolicy` resource, which serves as a template for defining security constraints. This resource allows administrators to specify a wide array of parameters, including the allowed volumes, capabilities, SELinux labels, and other security-related attributes that a pod must adhere to. For instance, a policy might restrict pods from using certain types of volumes such as `hostPath` or `emptyDir`, thereby limiting their access to host filesystems. Similarly, it can define which Linux capabilities (e.g., `CAP_NET_BIND_SERVICE`) are permitted, ensuring that pods cannot gain unnecessary privileges that could compromise the cluster’s security.

The admission controller is the next critical component of the PSP architecture. It acts as a gatekeeper, intercepting pod creation requests and evaluating them against the defined policies. When a pod specification is submitted, the admission controller checks whether it complies with any active PodSecurityPolicy. If the pod meets all the policy requirements, it is allowed to proceed; otherwise, an error is returned, preventing the pod from being scheduled. This mechanism ensures that security constraints are consistently applied across the cluster, regardless of the namespace or deployment method used.

The enforcement mechanism is responsible for translating the policy definitions into actionable security controls within the Kubernetes runtime. This involves integrating with the kubelet, which enforces the policies at the node level by applying security context settings to each pod. For example, a policy that specifies a particular SELinux label will be enforced by the kubelet when scheduling the pod, ensuring that the pod runs under the correct security context. Additionally, the enforcement mechanism may interact with other components such as the container runtime (e.g., Docker or containerd) to apply capabilities and resource limits defined in the policy.

The design of PSP is rooted in its ability to enforce a comprehensive set of security constraints, making it particularly well-suited for environments where strict security policies are required. However, this granularity comes at the cost of complexity. The need to define and maintain multiple policies for different use cases can lead to operational overhead, especially in large-scale clusters. Furthermore, the PSP model is tightly coupled with the kubelet, which can introduce challenges in terms of scalability and fault tolerance. These limitations have led to the development of alternative mechanisms such as PodSecurity, which offers a more streamlined approach while retaining many of the core security features of PSP.

The architecture of PodSecurityPolicy also supports a layered approach to security enforcement, allowing administrators to define policies at different levels of abstraction. For instance, a cluster-wide policy might enforce minimal privilege by restricting capabilities and volume types, while namespace-specific policies can introduce additional constraints tailored to specific workloads. This flexibility enables organizations to implement a defense-in-depth strategy, where multiple layers of security controls work together to mitigate potential vulnerabilities.

In terms of implementation, the PodSecurityPolicy resource is defined using a structured YAML format, with fields that specify the exact constraints to be enforced. For example, the `allowedCapabilities` field can be used to restrict the Linux capabilities available to pods, while the `seLinuxOptions` field allows administrators to define specific SELinux labels. These fields are then evaluated by the admission controller during pod creation, ensuring that each pod adheres to the defined security policies.

The design of PSP also includes support for various security contexts, such as runAsUser, runAsGroup, and fsGroup, which allow administrators to control the user and group identities under which pods execute. This is particularly important in multi-tenant environments, where different users or teams may require different levels of access. By defining these security contexts within a PodSecurityPolicy, administrators can ensure that pods are executed with the appropriate permissions, reducing the risk of privilege escalation attacks.

Another key aspect of the PSP architecture is its ability to enforce resource limits and quotas. While this is typically managed through Kubernetes' built-in resource management features, PSP can be extended to include additional constraints on CPU, memory, and other resources. This allows administrators to define policies that not only restrict privileges but also limit the resources a pod can consume, ensuring efficient utilization of cluster resources while maintaining security.

In summary, the PodSecurityPolicy architecture is designed to provide a robust framework for enforcing security constraints at the pod level within Kubernetes. By combining policy definitions, admission control, and enforcement mechanisms, PSP enables administrators to implement comprehensive security policies that align with their organizational requirements. While the design introduces complexity and certain limitations, it offers a granular and flexible approach to securing workloads, making it a valuable tool in environments where strict security controls are essential. The next section will explore the broader implications of PodSecurityPolicy within the context of Kubernetes security frameworks, including its integration with other components such as NetworkPolicies and RBAC.

### Enforcement Mechanisms and Integration

The enforcement of PodSecurity Policies (PSPs) and runtime constraints in a Kubernetes environment requires robust mechanisms that ensure policies are consistently applied across all nodes and pods. These mechanisms must integrate seamlessly with the core components of Kubernetes, such as the kubelet, kube-apiserver, and kube-proxy, while also leveraging external tools like admission controllers and network policy agents. The enforcement is further enhanced by the use of runtime constraints such as Seccomp, AppArmor, and SELinux, which provide additional layers of security at the container level. These mechanisms are critical for maintaining a hardened security baseline in air-gapped or regulated Kubernetes environments, where strict control over pod configurations and resource usage is paramount.

At the heart of PodSecurity Policy enforcement lies the admission controller, specifically the `PodSecurity` admission controller introduced in Kubernetes 1.25. This controller validates whether a pod meets the security requirements defined by the PodSecurityPolicy (PSP) or the newer PodSecurity standard. The `PodSecurity` admission controller ensures that all pods are evaluated against predefined policies before they are scheduled onto nodes. This validation includes checking for privilege escalation, container runtime capabilities, and other security-related attributes. By integrating this controller into the kube-apiserver, the enforcement of PSPs becomes a built-in feature of the Kubernetes control plane, ensuring that even in distributed environments, all pods adhere to the defined security policies.

The integration of PodSecurity Policies with runtime constraints is further strengthened through the use of admission webhooks and policy controllers. These components allow for dynamic enforcement based on real-time data and policy updates. For example, the `PodSecurity` admission controller can be configured to enforce specific security profiles such as `baseline`, `restricted`, or `privileged`, each corresponding to a different level of security posture. This flexibility enables administrators to tailor their security policies to the specific needs of their environment, whether it's a highly regulated financial institution requiring strict isolation or a cloud-native application needing minimal privileges for operational efficiency.

In addition to the admission controller, the enforcement of PodSecurity Policies is supported by runtime constraints such as Seccomp, AppArmor, and SELinux. These mechanisms operate at the container level, providing fine-grained control over system calls, process capabilities, and file system access. For instance, Seccomp can be configured to limit the set of system calls a container can make, thereby reducing the attack surface. Similarly, AppArmor and SELinux enforce security policies based on predefined profiles, ensuring that containers operate within defined boundaries. These runtime constraints are often integrated with PodSecurity Policies through configuration files or annotations, allowing for a unified approach to security enforcement.

The integration of these mechanisms is further enhanced by the use of kubelet’s built-in capabilities. The kubelet, which runs on each node and manages pod lifecycle operations, plays a critical role in enforcing PodSecurity Policies at runtime. When a pod is scheduled onto a node, the kubelet applies the relevant security policies and constraints based on the PodSecurityPolicy or PodSecurity configuration. This ensures that even if a policy is defined at the cluster level, it is enforced consistently across all nodes. The kubelet also supports the use of cgroups and other resource management features to limit CPU, memory, and I/O usage, further enhancing the runtime constraints applied to pods.

Another key component in the enforcement of PodSecurity Policies is the use of network policy agents such as Calico or Cilium. These tools provide additional layers of security by enforcing network policies that restrict pod communication based on defined rules. For example, a network policy can be configured to allow only specific pods to communicate with each other or to limit access to certain ports and IP ranges. By integrating these network policy agents with PodSecurity Policies, administrators can create a comprehensive security framework that addresses both runtime and network-level constraints.

The enforcement of PodSecurity Policies is also supported by the use of audit logs and monitoring tools. These tools provide visibility into pod operations and allow administrators to track compliance with security policies over time. For instance, audit logs can be used to detect violations of PodSecurity Policies or to identify patterns of non-compliant behavior. Monitoring tools such as Prometheus and Grafana can be configured to alert administrators when certain thresholds are exceeded or when specific security policies are not being adhered to. This real-time monitoring capability is essential for maintaining a proactive security posture in dynamic Kubernetes environments.

The integration of these enforcement mechanisms is further enhanced by the use of policy-as-code frameworks such as Open Policy Agent (OPA) and Gatekeeper. These tools allow administrators to define security policies in a declarative format, making it easier to manage and enforce complex security rules across the cluster. For example, OPA can be used to evaluate PodSecurity Policies against incoming pod configurations, ensuring that all pods meet the required security standards before they are scheduled. Similarly, Gatekeeper provides a way to enforce Kubernetes policies using custom constraints, which can be integrated with existing PodSecurity Policies to create a more robust security framework.

In addition to these tools, the use of service meshes such as Istio or Linkerd can further enhance the enforcement of PodSecurity Policies by providing additional layers of security and control. These service meshes can be configured to enforce network policies, limit access to services, and monitor pod behavior in real time. By integrating service meshes with PodSecurity Policies, administrators can create a more comprehensive security strategy that addresses both runtime and network-level constraints.

The enforcement of PodSecurity Policies is also supported by the use of container image scanning tools such as Clair or Trivy. These tools analyze container images for vulnerabilities and ensure that only secure images are used in the cluster. By integrating these tools with PodSecurity Policies, administrators can enforce not only runtime constraints but also image-level security requirements, ensuring that all pods operate within a secure environment.

Finally, the integration of these enforcement mechanisms is further enhanced by the use of automation and orchestration tools such as Helm and Kustomize. These tools allow administrators to define and apply security policies across multiple clusters and environments, ensuring consistency and reducing the risk of human error. By leveraging these tools, administrators can create a more scalable and maintainable security framework that adapts to the evolving needs of their Kubernetes environment.

In conclusion, the enforcement of PodSecurity Policies and runtime constraints in a Kubernetes environment requires a combination of admission controllers, runtime constraints, and integration with various tools and frameworks. These mechanisms work together to ensure that all pods meet the defined security requirements, providing a robust and consistent security baseline for air-gapped or regulated environments. By leveraging these enforcement mechanisms, administrators can create a comprehensive security strategy that addresses both runtime and network-level constraints, ensuring the integrity and confidentiality of their Kubernetes clusters.

### Runtime Constraint Evaluation Logic

The runtime constraint evaluation logic in bastionkit is a critical component of the PodSecurity Policies and Runtime Constraints framework, ensuring that all pod-level security requirements are rigorously enforced at runtime. This logic operates within the Kubernetes control plane, specifically leveraging the kubelet and kube-proxy components to apply security policies dynamically as containers are scheduled and executed. The evaluation process begins with the parsing of the PodSecurityPolicy (PSP) definitions, which are stored in the etcd database and accessible via the Kubernetes API. These policies define constraints on various aspects of pod creation, including privilege levels, seccomp profiles, SELinux labels, and AppArmor configurations. The runtime constraint evaluation logic is responsible for validating these constraints against the actual pod specifications as they are submitted to the kubelet.

At the heart of this evaluation process is the enforcement of PodSecurityPolicy (PSP) rules through the use of the `PodSecurity` admission controller. This controller is integrated into the Kubernetes API server and operates as a webhook, intercepting pod creation requests before they are admitted into the cluster. The `PodSecurity` admission controller evaluates the pod's security context against the configured PSPs and applies any necessary modifications or rejections based on the policy rules. For example, if a pod specification requests elevated privileges (such as the `privileged` flag), the admission controller will check whether this is allowed under the current PSP configuration. If not, the pod creation request is denied, preventing potentially insecure workloads from being scheduled.

The runtime constraint evaluation logic also extends to the enforcement of security context constraints at the container level. This includes the application of seccomp profiles, which are defined in the PSP and applied to containers via the `seccompProfile` field in the pod specification. The kubelet is responsible for loading these profiles into the container runtime (such as Docker or containerd) and ensuring that they are enforced during container execution. Similarly, SELinux and AppArmor policies are applied based on the PSP definitions, with the kubelet acting as the intermediary between the policy definitions and the underlying operating system. These security context constraints are critical for isolating containers from the host environment and limiting their access to system resources.

In addition to enforcing PodSecurityPolicy rules, the runtime constraint evaluation logic also integrates with Kubernetes' NetworkPolicy framework to ensure that pod-level network constraints are applied consistently across the cluster. The NetworkPolicy resource defines how pods can communicate with each other and with external networks, specifying allowed ingress and egress traffic based on label selectors. The runtime constraint evaluation logic ensures that these policies are enforced at the network level by leveraging the kube-proxy component and the Cilium or Calico network plugins. For example, if a pod is configured to only allow traffic from specific namespaces or labels, the network policy enforcement mechanism will block all other traffic, preventing unauthorized communication between pods.

The evaluation of runtime constraints also involves the enforcement of resource quotas and limits, which are defined in Kubernetes' ResourceQuota and LimitRange objects. These objects define the maximum amount of CPU, memory, and storage that can be consumed by a namespace or pod, ensuring that workloads do not exceed predefined thresholds. The runtime constraint evaluation logic integrates with the kubelet and kube-apiserver to enforce these quotas dynamically, preventing resource exhaustion and ensuring fair allocation of cluster resources. For instance, if a namespace has a defined CPU limit of 10 cores, any pod attempting to request more than this limit will be rejected by the admission controller, preventing overutilization of cluster resources.

The runtime constraint evaluation logic also incorporates the enforcement of Role-Based Access Control (RBAC) policies, ensuring that only authorized users and services can create or modify pods that meet the security constraints. RBAC policies are defined in Kubernetes' Role and ClusterRole objects, which specify the permissions associated with specific roles. The kube-apiserver enforces these policies by checking whether the requesting user has the necessary permissions to perform the requested action. For example, if a user attempts to create a pod that violates a PodSecurityPolicy, the RBAC enforcement mechanism will check whether the user is authorized to do so, and if not, the request will be denied.

The evaluation of runtime constraints is further enhanced by the use of admission controllers such as `PodSecurity`, `NamespaceLifecycle`, and `DefaultStorageClass`. These controllers work in conjunction with the runtime constraint evaluation logic to ensure that all pods meet the required security and resource constraints. For instance, the `PodSecurity` admission controller ensures that all pods are subject to the PodSecurityPolicy rules, while the `NamespaceLifecycle` controller enforces lifecycle policies such as namespace finalizers, ensuring that pods are properly cleaned up when a namespace is deleted.

Finally, the runtime constraint evaluation logic includes the enforcement of security context constraints at the container level, such as the `runAsUser`, `runAsGroup`, and `fsGroup` fields in the pod specification. These fields define the user and group IDs under which containers are executed, ensuring that containers run with minimal privileges and access to system resources. The kubelet is responsible for enforcing these constraints by mapping the specified user and group IDs to the underlying operating system, preventing privilege escalation and unauthorized access to file systems.

In summary, the runtime constraint evaluation logic in bastionkit ensures that all pods meet the required security and resource constraints at runtime. This logic operates through a combination of admission controllers, kubelet enforcement, and integration with Kubernetes' core components such as the API server, network plugins, and RBAC framework. By rigorously enforcing PodSecurityPolicy rules, network policies, resource quotas, and RBAC permissions, bastionkit provides a robust security baseline for air-gapped and regulated Kubernetes environments. This evaluation logic is essential for maintaining the integrity and confidentiality of workloads, preventing unauthorized access, and ensuring that all pods operate within predefined security boundaries.

### Namespace-Level Security Constraints

Namespace-Level Security Constraints are a critical component in enforcing runtime security policies within Kubernetes environments, particularly when applying PodSecurity Policies (PSPs) and other runtime constraints. At the heart of this mechanism lies the Namespace object, which serves as an abstraction layer to group related resources and apply security policies at a granular level. By leveraging Namespaces, administrators can enforce isolation, limit resource usage, and apply specific security constraints that are tailored to the needs of different workloads within the cluster.

The primary method for applying namespace-level security constraints is through the use of Kubernetes NetworkPolicy objects. These policies define how pods can communicate with each other and with external networks, thereby enabling fine-grained control over network traffic. For instance, a NetworkPolicy can restrict pod-to-pod communication to only those within the same Namespace or limit access to specific services based on label selectors. This approach ensures that even if a pod within a Namespace is compromised, it cannot easily communicate with other pods in different Namespaces, thereby reducing the attack surface.

In addition to NetworkPolicies, PodSecurity Policies can be applied at the Namespace level to enforce security standards for all pods running within that Namespace. These policies define constraints such as the minimum required security context for pods, including user IDs, group IDs, and runAsNonRoot settings. For example, a PodSecurity Policy might require all pods in a Namespace to run as non-root users, thereby reducing the risk of privilege escalation attacks. By applying these policies at the Namespace level, administrators can ensure that all workloads within a specific security context adhere to consistent security standards.

Furthermore, Namespaces can be used to enforce resource quotas and limits, which are essential for maintaining stability and preventing resource exhaustion. Resource quotas define the maximum amount of CPU, memory, and other resources that can be consumed by pods within a Namespace. By setting appropriate quotas, administrators can ensure that no single workload consumes an excessive amount of resources, thereby preventing potential outages or performance degradation. This is particularly important in regulated environments where resource usage must be closely monitored and controlled.

Another key aspect of namespace-level security constraints is the use of Role-Based Access Control (RBAC) to define permissions at the Namespace level. RBAC allows administrators to assign specific permissions to users or service accounts, ensuring that they can only access resources within their designated Namespace. For example, a developer might be granted read-only access to a development Namespace but not to production Namespaces, thereby reducing the risk of accidental or intentional modifications to critical workloads. This granular control over access ensures that security policies are consistently enforced across the cluster.

In addition to these mechanisms, Namespaces can also be used to enforce specific security configurations such as seccomp and AppArmor profiles. These profiles define the system call filters and application-specific security policies that are applied to containers running within a Namespace. By applying these profiles at the Namespace level, administrators can ensure that all containers within a specific security context adhere to consistent security standards, regardless of the underlying workload or application.

Moreover, Namespaces can be used in conjunction with Kubernetes Admission Controllers to enforce additional security constraints during pod creation. Admission controllers such as PodSecurityPolicyAdmissionController can validate that pods meet the required security policies before they are scheduled on nodes. This ensures that even if a pod is created outside of the Namespace-level constraints, it still adheres to the overall security policy defined for the cluster.

In regulated environments, the use of Namespaces for security constraints is often mandated by compliance frameworks such as ISO 27001, NIST SP 800-53, and GDPR. These frameworks require organizations to implement strict access controls, resource limits, and network segmentation to protect sensitive data and ensure regulatory compliance. By leveraging Namespaces, administrators can meet these requirements by creating isolated environments that are tailored to specific security needs.

The effectiveness of namespace-level security constraints is further enhanced by the use of monitoring and logging tools that provide visibility into the security posture of each Namespace. Tools such as Prometheus, Grafana, and ELK stack can be used to monitor resource usage, network traffic, and security events within each Namespace. This visibility enables administrators to detect anomalies, respond to security incidents, and continuously improve their security policies.

In summary, namespace-level security constraints are a powerful mechanism for enforcing runtime security policies within Kubernetes environments. By leveraging NetworkPolicies, PodSecurity Policies, RBAC, resource quotas, and admission controllers, administrators can create isolated and secure environments that meet the specific needs of different workloads. This approach not only enhances the overall security of the cluster but also ensures compliance with regulatory requirements in regulated environments.
